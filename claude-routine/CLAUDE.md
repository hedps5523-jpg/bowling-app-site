# 전역 작업 루틴 (모든 프로젝트 공통)

## 1. 모델 선택 루틴 (사용량 효율 우선)
- 기본 모델은 Sonnet 5.5 이다. 대부분의 개발 작업(구현, 수정, 버그 수정, 리뷰, 테스트)은 Sonnet 이 직접 처리한다.
- 단순 작업은 `haiku-helper` 서브에이전트(Haiku)로 보낸다.
  예: 파일·문자열 검색, 목록 정리, 포맷 변환, 짧은 요약, 로그 추려 읽기, ZIP/파일 존재 확인, 반복적인 일괄 치환.
- 어려운 작업은 `opus-advisor` 서브에이전트(Opus)로 보낸다. 판단이 많이 필요한 경우에만 쓴다.
  예: 아키텍처·구조 설계, 원인 불명 버그의 근본 원인 분석, 여러 모듈에 걸친 영향 분석, 보안·데이터 마이그레이션 같은 되돌리기 어려운 결정.
- 판단이 애매하면 Sonnet 으로 진행한다. Opus 는 Sonnet 이 막혔을 때(2회 이상 같은 방식으로 실패)도 호출한다.
- Opus/Haiku 호출은 결과 요약만 받아 쓰고, 같은 조사를 중복하지 않는다.

## 2. 작업규칙 확인 루틴 (앱 작업 시 가장 먼저)
- 앱 작업을 시작하면 코드를 보기 전에 `E:\working` 의 해당 프로그램 작업규칙 `.md` 파일을 먼저 읽는다.
  - My_Folder → 수정본_MyFolder_작업규칙_통합정리_최신.md
  - 모바일 볼링클럽 → 수정본_MobileBowlingClub_작업규칙_통합정리_최신.md
  - 팀메이커 → 수정본_Team_Maker_작업규칙_통합정리_최신.md
  - 볼로그 → 수정본_BowlingNote_작업규칙_통합정리_최신.md
  - ReceiptRoad(MoneyMile) → 수정본_ReceiptRoad_작업규칙_통합정리_최신.md
  (정확한 파일명이 다르면 E:\working 에서 프로그램명으로 찾는다.)
- 해당 프로그램의 규칙만 읽고, 다른 프로그램의 경로·규칙·소스는 섞지 않는다.
- 규칙 파일을 읽을 수 없거나 누적소스 READ/WRITE 확인이 실패하면 추정·우회하지 말고 원인을 알리고 사용자에게 계속할지 묻는다.
- 규칙 우선순위: 해당 프로그램 MASTER 규칙 → 작업화면 룰 → 그 외. 이 전역 루틴은 프로그램 규칙과 충돌하면 프로그램 규칙에 양보한다.

## 3. 응답 방식
- 말투는 부드럽게, 작업 과정 표시는 짧게 정리한다. 상세 설명 요청(장문, 길게 등)이 있으면 최대한 상세하고 정확하게 쓴다.
- 작업 과정은 명령어·내부 로그를 늘어놓지 않고 4단계 문구로만 알린다.
  1단계: 수정 적용 방향 정리중...... / 2단계: 소스파일에 적용중...... / 3단계: 수정 적용된 최종 점검중....... / 4단계: 결과 출력합니다.
- 결과물에 정말 중요한 변경(패키지명, 서버 구조, 삭제, 버전업 등)이 있으면 먼저 사용자 승인을 받는다.
- 버전은 요청이 없으면 올리지 않는다. 올릴 때는 현재 값과 권장안(마지막 자리 +1)을 보여주고 응답받은 값을 적용한다.

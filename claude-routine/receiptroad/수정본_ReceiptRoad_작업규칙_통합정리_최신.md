## [MASTER 실행 우선 규칙]

1. 본 규칙은 ReceiptRoad 작업에서 최우선 적용되는 실행 기준이다. 우선순위는 MASTER 규칙 → 작업화면 룰(A-4) → 그 외 항목 순이며, 문서 끝의 날짜별 추가 구간은 기존 항목과 충돌할 때 그쪽을 우선한다.
2. 사용자가 수정, 적용, 진행, 반영, 작업진행, 구현, 변경, 생성 등 실제 작업 의미가 포함된 요청을 하면 설명 요청이 아닌 실제 작업 수행 요청으로 해석한다. 분석·설명·방법 제시만 하고 종료하지 않는다.
3. 단, '시안'만 있고 진행 의미가 없으면 소스를 고치지 않고 시안만 만든다.
4. 실제 작업을 시작할 때는 다른 작업보다 먼저 누적소스 폴더(`D:\Pg_Edit\MoneyMile`)와 수정 대상 파일의 존재 및 READ/WRITE 권한을 확인한다. READ 또는 WRITE 중 하나라도 실패하거나 정상 여부를 확인할 수 없으면 즉시 문제 항목과 확인된 원인을 사용자에게 알리고, 수정을 시작하지 않은 상태에서 계속할지 묻는다. 사용자 확인 전에는 다음 단계로 진행하지 않으며 권한 정상 여부를 추정하거나 우회하지 않는다.
5. 권한이 모두 정상으로 확인되면 별도 승인 질문 없이 본 작업규칙과 작업화면 룰(A-4)을 확인하고 즉시 다음 단계로 진행한다.
6. 실제 작업은 아래 순서로 진행한다.
   - 권한 확인 → 규칙 확인 → 작업화면 룰 확인 → 최신 누적소스 확인 → 수정 대상 확인 → 수정 → 영향 범위 점검 → 검증 → 결과물 생성 → 누적소스 반영 → 백업 → 보고
7. 수정 가능한 작업임에도 코드 예시·수정 방향·예상 구조 설명만 제공하고 실제 작업 단계로 진입하지 않는 것은 작업 미완료로 판단한다. 실제 수정이 불가능하면 불가능한 원인과 필요한 다음 단계를 명확히 제시한다.
8. 작업 완료 판단 기준은 답변 작성 여부가 아니라 실제 변경 결과, 검증 결과, 결과물 반영 여부이다.

## A. 작업과정에 대한 룰

### [A-1. 요청 해석]
1. 수정·적용·진행·반영 등의 표현이 있으면 실제 작업으로 해석한다.
2. 요청에 '시안' 또는 '1차시안'만 있고 진행 의미가 없으면 실제 소스를 수정하지 않고 시안을 먼저 만든다. '진행', '작업진행', '승인하고 진행해' 등 진행 의미가 함께 있으면 별도 승인 질문 없이 실제 소스에 적용한다. 시안 문구가 없으면 바로 적용한다.
3. 사용자가 '추가 내용'이라고 한 항목은 현재 진행 중인 수정과 하나의 변경 세트로 통합하고 별도 버전으로 쪼개지 않는다.
4. 요청과 직접 연결된 부분만 작업 대상으로 한다. 요청받지 않은 이미지 생성, 전면 재설계, 메뉴 삭제, 데이터 구조 변경은 하지 않는다.

### [A-2. 작업 시작 순서]
1. 권한 확인(MASTER 4) → 규칙 확인 → 작업화면 룰(A-4) 확인 → 최신 누적소스 확인 → 수정 대상 확인 순으로 시작한다.
2. 최신 누적소스는 `D:\Pg_Edit\MoneyMile`이다. 원본 ZIP은 복구·대조용이며 누적소스가 정상이면 기준으로 쓰지 않는다. 누적소스와 `E:\working\MoneyMile`, `E:\working\backup\MoneyMile`의 내용이 다르면 누적소스를 기준으로 한다.
3. 현재 versionName/versionCode와 최근 변경 ZIP을 비교하여 가장 최신의 정상 상태를 작업 기준으로 잡는다.
4. 실제 Gradle sourceSet에 포함된 파일만 수정한다. 같은 이름의 중복 소스가 있어도 sourceSet 밖의 파일은 수정하지 않는다.
5. 수정 전에 관련 Activity/Screen/Repository/Manager/View 연결과 공통 영향 범위를 확인한다.

### [A-3. 수정 전 백업, 최소 변경]
1. 수정 전에 백업을 만든다.
2. 기존 메뉴·탭·화면 폼·화면 이동·데이터 저장 규칙은 유지하고, 요청과 직접 연결된 부분만 고친다. 화면 전체 재작성보다 기존 컴포넌트의 최소 변경을 우선한다.
3. 다른 프로그램(볼링클럽 계열 등)의 UI/소스는 참고만 하고 그대로 복사·덮어쓰지 않는다.
4. 기존 규칙의 문장은 사용자가 명시적으로 지정하기 전에는 바꾸지 않는다.

### [A-4. 작업 진행과정 화면 표시]
1. 실제 수정 작업 중 사용자 화면에는 다음 두 종류의 문구만 표시한다.
   - 아래 4단계 진행 문구
   - 현재 작업의 목적 또는 결과를 설명하는 상위 작업 요약 한 줄(작업 묶음마다 한 줄, 연속 설명·세부 목록 금지)
2. 기본 진행 화면은 아래 4단계만 보여준다.
   1. 수정 적용 방향 정리중......
   2. 소스파일에 적용중......
   3. 수정 완료된 소스파일 최종 점검중......
   4. 결과 출력합니다.
3. 명령어, 함수명, 클래스명, 내부 도구명, 파일 탐색 과정, 개별 파일 확인 과정, 컴파일 세부 로그, 원시 오류 로그, 내부 파라미터, 임시 파일명, 작업용 경로, 내부 도구 사용 기록, 여러 줄의 세부 처리 목록은 사용자 화면에 표시하지 않는다.
4. 4단계 '결과 출력합니다.'에서는 최종 결과만 핵심 위주로 간략히 표시한다. 최소 표시 내용:
   - 수정·변경된 내용 요약
   - 실제 소스파일에 적용된 내용 요약
   - 컴파일/정적 점검 및 결과물 반영 여부
   - 누적소스 반영 여부
   - 백업 ZIP 저장 여부
   - 추가로 업데이트하면 좋은 내용이 있는 경우 조언
5. 누적소스 반영 여부와 백업 ZIP 저장 여부는 서로 다른 항목이므로 한 줄로 합치지 않고, 각각 독립된 굵은 줄로 실제 상태에 맞는 문구 하나를 표시한다.
   - **누적소스 반영 여부: 반영 완료**
   - **누적소스 반영 여부: 미반영**
   - **누적소스 반영 여부: 해당 없음**
   - **백업 ZIP 저장 여부: 저장 완료**
   - **백업 ZIP 저장 여부: 미저장 (원인과 남은 조치)**
   - **백업 ZIP 저장 여부: 해당 없음**
6. 소스를 누적소스 폴더에 직접 수정·저장했다면 '누적소스 반영 여부'는 '반영 완료'이다. 백업 ZIP이 아직 없다는 이유로 '미반영'으로 표시하지 않는다.
7. 외부기기·외부 저장장치·USB 등 현재 환경 밖의 장치에 접근하려면 사용자 승인이 필요하다. 이때는 '외부기기 접근 승인이 필요합니다.'라고 표시하고 승인 전에는 진행하지 않는다.
8. 오류가 발생해도 장문의 내부 로그를 진행 화면에 출력하지 않는다. 중단된 큰 단계만 간단히 표시하고 최종 결과에서 실패 원인과 필요한 다음 조치만 요약한다.
9. 정보 신뢰성: 실제로 확인한 사실만 표시한다. 확인하지 못한 것은 '확인됨', '문제 없음', '완료' 등 확신하는 표현을 쓰지 않고 '미확인' 또는 '확인 필요'로 적는다. 추정·예상을 사실처럼 표시하지 않는다.

### [A-5. 수정 후 점검]
1. 작업 대상이 ReceiptRoad(`D:\Pg_Edit\MoneyMile`)인지 확인한다.
2. 최신 누적소스와 작업 버전이 일치하는지, 실제 sourceSet 경로만 수정했는지 확인한다.
3. 영향 범위(연결된 화면·저장 구조·OCR 처리·네트워크 처리)를 점검한다.
4. 영수증 OCR 관련 작업 시 촬영/갤러리 불러오기, 인식 결과 수정, 저장, 원본 이미지 보관 흐름이 기존대로 동작하는지 함께 점검한다.

9. versionName/versionCode, 변경 ZIP 구조, ZIP 무결성, 누적소스 반영 여부를 최종 확인한다.

## B. 결과물에 대한 룰

### [B-1. 버전]
1. 사용자가 버전업을 요청하지 않으면 버전을 올리지 않는다. 일반 기능 추가·UI 변경·동작 변경·분석·점검·규칙정리만으로는 versionName/versionCode를 현재 값 그대로 유지한다.
2. 직전 수정 때문에 생긴 컴파일 오류·경고·오타·동일 기능의 단순 버그 패치는 같은 버전을 유지한다.
3. 사용자가 명시적으로 버전 유지 또는 변경을 지시하면 그 지시를 따른다.
4. versionName, versionCode, 화면에 표시되는 버전값이 있으면 서로 일치시킨다.

### [B-2. 변경 ZIP, 변경 파일 명칭]
1. 변경 ZIP에는 실제 변경된 파일만 넣는다. 프로젝트 루트 상대경로를 유지하고 상위 래퍼 폴더는 만들지 않는다. 버전 변경 작업에서는 버전값이 들어 있는 Gradle 파일을 반드시 포함한다.
2. 저장 위치: `E:\working\MoneyMile`
3. 변경 ZIP 파일명 기본형: `ReceiptRoad_V<버전>_ChangedFiles_mm_dd_HHmm.zip` (예: `ReceiptRoad_V1.0.0_ChangedFiles_11_03_2230.zip`). 컴파일 전용 패치는 `ReceiptRoad_V<버전>_CompileFix_ChangedFiles_mm_dd_HHmm.zip`을 쓸 수 있다.
4. 변경 ZIP·변경 파일 사본의 파일명 맨 끝(확장자 앞)에 작업 완료 시점의 `_mm_dd_HHmm`(월·일·24시간제 시분, 연도 제외)을 붙인다. 프로젝트 소스 안에 적용되는 파일은 클래스명·참조 오류 방지를 위해 원래 파일명을 유지한다.
5. 같은 이름의 변경 ZIP을 덮어쓰지 않고 수정 때마다 새 일자+시간 이름으로 만든다. 이전 변경 ZIP은 사용자가 지시하기 전에는 삭제하지 않는다.
6. ZIP 생성 후 파일 목록, 상대경로, 무결성을 확인한다.

### [B-3. 누적소스 반영]
1. 수정한 모든 파일은 완료 전에 `D:\Pg_Edit\MoneyMile`의 동일 프로젝트 상대경로에 반영한다. 반영에 실패하면 완료로 처리하지 않는다.
2. 로컬 임시 작업본만 최신 상태로 남겨두지 않는다. 누적소스가 다음 작업의 최우선 기준이다.
